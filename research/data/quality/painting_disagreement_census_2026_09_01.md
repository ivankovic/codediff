# Rendering vs. painting: a full census of the `painting_agreement` corpus, 2026-09-01

**What this is.** For every fixture in `src/test/painting_agreement/` (the ones with both a
`Minimal` and/or `Full` hand-painted text ground truth), how much codediff's own rendering
disagrees with that painting under each preset, and - read by hand, one fixture at a time - *why*.
Companion to `text_painting_findings.md` (which is about what the two painting styles mean and the
rules a painter converges on); this is about where the renderer's byte-for-byte output diverges
from either painting and whether that divergence groups into a small number of causes.

**Method.** `compare_painting`/`ranges_for_options` (`src/test/helper/human_mapping.rs`) already
give the aggregate percentage per fixture per preset - that's what
`handmade_painting_disagreement_report` prints. A new batch diagnostic,
`painting_disagreement_detail_batch` (added to the same file, `#[ignore]`, not wired into any
default test run), dumps every contiguous byte run where "ours" (codediff's rendering under
`RenderOptions::MINIMAL`/`FULL`) and "theirs" (the human's painting) disagree, with side, row, byte
range and the literal text. Five parallel readers went through the 53 disagreeing fixtures'
dumped detail against the actual before/after source; the specific mechanism claims below were then
checked against the code directly (see "Verified vs. read once").

Reproduce the numbers:
```
cargo test --lib --features test-fixtures handmade_painting_disagreement_report -- --ignored --nocapture
FIXTURES="c-cpython-autogenerated-code,..." cargo test --lib --features test-fixtures measure_stub_fixtures -- --ignored --nocapture
```
Reproduce the byte-level detail for any fixture:
```
FIXTURES="<name>,<name>,..." cargo test --lib --features test-fixtures painting_disagreement_detail_batch -- --ignored --nocapture
```

**Scope.** 63 fixtures have a `painting_agreement` test. `handmade_painting_disagreement_report`
only scans `src/test/data/diffs/handmade` (55 of the 63); the other 6
(`c-cpython-autogenerated-code`, `c-ffmpeg-added-typedef-to-enum`, `c-freeciv-add-parameter-to-function`,
`c-htop-remove-function-declaration`, `c-microsoft-terminal-add-function`,
`javascript-typescript-interesting-small-edit-refactor`) live under `data/diffs/small` and are
**not** part of the 1.3401% aggregate that report prints. Measured separately with
`measure_stub_fixtures` and folded into this census, but not into that aggregate number.

**This 1.3401% (handmade-only, 55 fixtures) is not the same measurement as the 2026-09-01 baseline
memory's 1.8703%** - different scope, and the baseline memory needs an explicit re-measurement,
not a silent overwrite by this number.

10 of the 63 fixtures agree exactly (0.000% both presets) and are not analyzed further:
`java-add-logging`, `rust-add-value-to-enum`, `rust-hello-world-added-message`,
`rust-hello-world-removed-message`, `rust-no-change`, `rust-tauri-api-build-1`,
`rust-tauri-cli-ios-dev`, `rust-zed-git-panel-settings`, `c-htop-remove-function-declaration`,
`c-microsoft-terminal-add-function`.

## A confirmed bug, found while checking a fork's claim

`python-api-change`: a wholly new top-level function (`get_user_info`, ~10 lines) renders with
**zero highlighting** - not `Insert`, nothing - as if it were pre-existing unchanged text. Verified
directly against the real renderer, not just the test harness:

```
cargo run --bin codediff -- --headless --full --context 999 \
  src/test/data/diffs/handmade/python-api-change/before.py.test \
  src/test/data/diffs/handmade/python-api-change/after.py.test
```

Lines 23-33 of `after.py.test` print in plain, uncolored text. Root cause not yet found - plausibly
a bad hash-match pulling this new function's whole range onto something else - but this is a real
correctness gap, independent of any `RenderOptions` choice, and deserves its own investigation
before anything else in this file.

## Patterns

### 1. Single-row column-shift painted `Move` - deliberate calibration, not a bug

`rust-small-addition-with-reuse-of-binary-expressions` is itself a diff of codediff's own source,
and its `before`/`after` text carries the design comment directly: painting a single-row span that
only shifted column (because earlier text on its line grew or shrank) as `Move` is a **measured**
choice - 16 human-painted moves in the corpus are exactly this shape across 6 fixtures, and
excluding them regressed `rust-add-if` from 0.7% to 56.5% disagreement. Three past sessions already
tried and reverted heuristic fixes here (`[[project_move_projection_row_normalization_2026_08_30]]`,
`[[project_precise_mapping_vs_painting_measurement_2026_08_30]]`).

~15 fixtures below disagree with *their own* painting on this exact axis: `cpp-add-const-correctness`,
`typescript-add-generics`, `cpp-add-templates`, `java-fix-array-index`, `cpp-fix-segfault`,
`kotlin-fix-loop-bug`, `rust-tauri-api-build-2`, `c-ffmpeg-added-typedef-to-enum`,
`rust-sniffnet-protocol`, `rust-add-to-existing-use`, `java-add-interface`, `java-refactor-constants`,
`cpp-add-memory-management`, `javascript-fix-promises`, `rust-data-structure`, and - at much larger
scale - `typescript-add-type-annotations` (a multi-row node whose rows genuinely shifted, which by
the calibration's own "real relocation" branch also counts). None of these are levers to pull
without revisiting a decision already made three times.

### 2. "Reindent-only Move" recognition is scoped to one Rust construct

`paint_reindent_only_moves`/`solve_nested_condition_collapse`'s `known_pure_reindent` check only
recognizes Rust's `if let`-chain collapse. Wrapping existing code in a new block in any other
language or construct gets no exemption, so codediff paints the whole relocated body `Move` under
**both** presets regardless. That's fine when the fixture's own `Full` painting agrees (small
residual); it's a large gap when `Minimal`'s painting wants it unpainted and codediff only has the
`Full`-shaped answer:

| Fixture | Minimal % | Full % |
|---|---|---|
| java-add-exception-handling | 60.786 | 6.399 |
| rust-add-if | 59.420 | 1.087 |
| typescript-add-error-handling | 35.610 | 3.415 |
| python-added-if-block-small | 18.440 | 7.092 |
| python-added-if-block | 3.833 | 0.852 |

`rust-add-if` is previously investigated and its residual deliberately accepted (see project
memory) - three separate Move-heuristic fixes tried there and reverted for regressing other
fixtures.

### 3. A connecting-newline seam, distinct from pattern 4

Checked directly: `trim_trailing_whitespace` (`src/diff/text.rs`) correctly drops a genuinely
trailing isolated newline - traced the code, then confirmed empirically on
`rust-adding-to-a-list-of-identical-attributes-should-favour-near-matches`'s single-byte case (one
`\n`, twice, byte-identical in both presets). What's actually happening in the newline-only
disagreements below is different: one continuous AST-derived multi-row range straddles a seam
between two lines the human painted as two *separate* per-line entries. The connecting `\n` falls
inside codediff's one range (interior bytes of a range are never trimmed) but outside either human
entry. This is not the "never paint trailing whitespace" rule failing to fire.

Affected: `rust-adding-to-a-list-of-identical-attributes-should-favour-near-matches` (0.007%, the
cleanest single-byte case), `rust-adding-many-identical-cfg-test-statements-...` (0.533%), and
contributes part of the residual in `java-add-interface`, `kotlin-add-null-check`,
`rust-leetcode-1-bugfix`, `rust-sniffnet-protocol`, `typescript-refactor-interface`,
`rust-adding-a-variable-and-test-with-comments`, `rust-add-comments-and-real-new-logic`,
`c-cpython-autogenerated-code`.

### 4. Whole-block insert/delete keeps interior indentation whole - a real, mostly-unvalidated axis

`interior_line_indentation: true` in both `MINIMAL` and `FULL` means a wholly inserted or deleted
multi-line block paints every interior row's leading whitespace as part of the range. Several
fixtures' own `Minimal` ground truth instead trims each row to its own content (the rules doc's
indentation choice 2, which `RenderOptions::interior_line_indentation`'s own doc comment says "no
fixture in the corpus paints ... yet" - this census turned up candidates, not proof, since the
newline (pattern 3) and the indentation (this pattern) were not independently isolated per
fixture):

`cpp-optimize-algorithm` (6.550% → 0.319% Full), `javascript-add-array-method` (9.351% → 0.519%),
`kotlin-add-validation` (5.366% → 0.000%). Worth a second, more careful pass before treating these
as settled evidence for implementing choice 2.

### 5. Genuine matching-algorithm gaps - not reachable by any `RenderOptions` field

Restructurings the tree matcher doesn't bridge, so codediff does a flat Delete+Insert where a human
traces reuse:

- `kotlin-refactor-function` (60.888% / 59.885%, **worst in the corpus**) - two flat functions
  merged into a `data class` with two methods, reusing `width * height` / `2 * (width + height)`
  and renamed call sites. No bridge found at all.
- `javascript-add-destructuring` (25.373% / 24.478%) - four assignments collapse into one
  destructuring statement.
- `javascript-add-event-listener` (17.706% / 16.209%) - `.onclick =` → `.addEventListener(...)`,
  token reuse across differently-shaped nodes.
- `javascript-typescript-interesting-small-edit-refactor` (6.618% / 6.863%) - manual
  destructuring → `[a, b] = arr`.
- `rust-multi-map-duplicate-calls` (28.571% / 58.095%) - three identical calls collapse to two, a
  genuinely ambiguous identical-text tie-break where human and codediff pick different, equally
  defensible answers.
- `rust-algorithm-change` (25.823% / 28.807%) - rewritten for-loop header, different
  Update/Delete/Insert split.
- `rust-error-handling` (6.160% / 5.014%) - `.unwrap()` → `Ok(...)` wrap, Update-vs-Delete/Insert/Move
  tie-break.
- `python-bugfix-loop` (1.241% / 1.862%) - matches only leaf tokens where the human matches the
  whole rewritten `for … in … :` skeleton.
- Identifier-rename Update-vs-Delete+Insert granularity: `typescript-add-generics`,
  `c-cpython-autogenerated-code` (`tuple_length`→`length`), `c-ffmpeg-added-typedef-to-enum`
  (`unsigned`→`SwsCompFlags`), `rust-turbopack-persistence-tools-main`.

None of the 53 disagreeing fixtures trace to `structural_punctuation` or `whole_pair_updates` at
all.

## Verified vs. read once

Patterns 1 and 3's mechanisms, and the `python-api-change` bug, were independently checked against
the code and/or the real renderer in this session. Everything else - the per-fixture assignment to
a pattern, and roughly 42 of the 53 table rows below - came from five parallel agents reading the
`painting_disagreement_detail_batch` dump against fixture source, each covering ~10-11 fixtures,
**not independently re-verified**. Treat each row as one read, not a settled finding - in
particular `python-add-remove-block`'s "possible ground-truth inconsistency" and any row citing
pattern 4 should get a second look before being acted on.

## What this suggests, in rough order of confidence

1. **Root-cause `python-api-change`'s unpainted-Insert bug.** The one item here that's a plain
   defect, not a preference or a documented trade-off. Two-minute repro is in this file; root cause
   is not yet found.
2. **Split pattern 3 from pattern 4 with a purpose-built test**, rather than the read-once
   assignment in this census. `rust-adding-to-a-list-of-identical-attributes-...` at 0.007% is the
   cleanest pattern-3-only fixture to build a regression test around.
3. **Do not re-attempt a fix for pattern 1.** It's calibration, backed by a 16/6-fixture
   measurement, and reverted three times already. Any future session tempted to "fix" a
   column-shift-Move fixture should read `rust-small-addition-with-reuse-of-binary-expressions`'s
   own doc comment first.
4. **Decide the fix for pattern 2's scope** (generalize `known_pure_reindent` beyond Rust's if-let
   collapse, or accept the residual the way `rust-add-if` already is) - this is the largest
   single lever in the table by percentage-points affected (5 fixtures, up to 60.8%).
5. Pattern 5's fixtures are matching-algorithm gaps, not rendering gaps - out of scope for
   `RenderOptions` work entirely; would need `hash_tree_matching`/`grouped_greedy_matcher` changes.
